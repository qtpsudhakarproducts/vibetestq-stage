Architecture vs Selenium BiDi Protocol

The Problem with Old-School Automation

Selenium's Legacy Pain

  • WebDriver protocol: HTTP round-trip per action
  • External driver process (ChromeDriver, GeckoDriver)
  • No auto-waiting — need explicit waits everywhere
  • Flaky tests due to timing issues
  • No native API testing support

What Playwright Did Differently

  • Direct CDP/BiDi connection — no HTTP overhead
  • Bundled browser binaries — no driver version mismatch
  • Auto-waiting built into every action and assertion
  • Network interception at the protocol level
  • API testing built in — one tool for everything

Playwright was built by ex-Puppeteer team at Microsoft with lessons learned from every previous tool's failures.

Playwright Architecture: How It Really Works

Your Test

TypeScript/JS running in Node.js — your test code calls Playwright APIs.

Playwright Node

Translates API calls to browser commands via CDP (Chrome) or BiDi (all).

Browser Process

Chromium, Firefox, or WebKit running in isolated context. Bundled, versioned.

Browser Context = Isolated Session

Each test gets its own BrowserContext — isolated cookies, storage, cache. Multiple tests run truly parallel without interference.

Auto-Waiting — The Most Valuable Feature

Selenium Way — Manual Waiting

driver.get("https://app.com"); WebDriverWait(driver, 10).until( EC.presence_of_element_located((By.ID, "username")) ) driver.find_element(By.ID, "username").send_keys("admin") WebDriverWait(driver, 10).until( EC.element_to_be_clickable((By.ID, "login")) ) driver.find_element(By.ID, "login").click()

Playwright Way — Auto-Wait

await page.goto('https://app.com'); // Automatically waits for element to be: // visible, enabled, stable (no animation) await page.getByLabel('Username').fill('admin'); await page.getByRole('button', { name:'Login' }).click(); // No explicit waits needed!

Playwright checks: attached → visible → stable → enabled → focused — all before each action. This eliminates 90% of flaky tests.

The BiDi Protocol — The Future of Browser Automation

What is WebDriver BiDi?

  • W3C standard: bidirectional browser-to-driver communication
  • Replaces HTTP request/response with WebSocket stream
  • Real-time event subscription (console, network, DOM)
  • Playwright uses BiDi for Firefox and Safari

BiDi vs CDP

  • CDP (Chrome DevTools Protocol) — Chrome/Chromium only
  • BiDi — cross-browser standard (W3C backed)
  • Playwright uses both and abstracts the difference
  • Future: all browsers BiDi-native

BiDi enables features impossible with old WebDriver: console log capture, network event streaming, JS exception monitoring.

Playwright MCP — AI Meets Browser Automation

What is Playwright MCP?

MCP (Model Context Protocol) is an open standard that lets AI assistants control tools. The official @playwright/mcp package exposes Playwright as an MCP server, letting AI agents browse the web and generate tests.

What It Enables

  • Claude, Copilot uses browser via Playwright
  • AI can inspect pages, click, fill forms
  • Generate test code from live interaction
  • Debug tests by having AI reproduce failures

Setup (VS Code Co-pilot / Cursor)

npx @playwright/mcp@latest # Adds Playwright as a tool available # to your AI assistant in Cursor or # VS Code Copilot Agent mode
