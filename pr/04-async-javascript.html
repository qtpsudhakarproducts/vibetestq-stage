Why Does Async Exist?

The Problem

Browsers and Node.js are single-threaded. They can only do one thing at a time.

Waiting for a network request, a file read, or a page to load would freeze everything if done synchronously.

The Real-World Analogy

You order coffee at a cafe. You don't stand frozen until it's ready. You sit down, check your phone, and the barista calls you when it's done.

That's async: start a task, do other work, handle result when ready.

Every Playwright action — page.goto(), page.click(), expect().toBeVisible() — is async. This is why you need await.

The Order Problem — Why Tests Break Without Async

❌ Without await

// Steps fire immediately — no waiting page.goto('/login'); // starts, doesn't wait page.fill('#u', 'admin'); // page not loaded yet! page.click('#submit'); // form not filled yet! // Test FAILS — steps ran out of order
  • Button clicked before page loaded
  • Form submitted before filled
  • Random failures, hard to debug

✅ With await

// Each step waits for the previous await page.goto('/login'); // waits for load await page.fill('#u', 'admin'); // waits for fill await page.click('#submit'); // waits for click // Exact sequence, every time
  • Each step confirms completion before next
  • Playwright verifies element is ready
  • Reliable, deterministic test flow

This is the #1 reason await exists in Playwright — it enforces step order. Forgetting it causes random, hard-to-reproduce failures.

The Evolution of Async Patterns

Era 1 — 1995–2012

Callbacks — Functions passed as arguments, called when async work is done. Worked but led to "Callback Hell".

Era 2 — ES6 2015

Promises — Objects representing a future value. Chainable with .then() and .catch(). Much cleaner but still verbose.

Era 3 — ES2017 ← We Are Here

async/await — Syntactic sugar over Promises. Reads like synchronous code. Used in every Playwright test.

Understanding all three eras means you can debug any async error you encounter.

Era 1: Callbacks

// Callback pattern — basic form function fetchUser(id, callback) { setTimeout(() => { const user = { id, name: "Admin" }; // simulated async result callback(null, user); // convention: error first, then data }, 1000); } fetchUser(1, function(error, user) { if (error) { console.error(error); return; } console.log(user.name); }); // CALLBACK HELL — nested async operations getUser(id, function(err, user) { if (err) return handleError(err); getOrders(user.id, function(err, orders) { if (err) return handleError(err); getOrderDetails(orders[0].id, function(err, details) { if (err) return handleError(err); // ... 5 more levels deep }); }); });

Callback hell = unmaintainable, hard to debug, error handling repeated everywhere. This is why Promises were created.

Era 2: Promises

// Creating a Promise const fetchUser = (id) => new Promise((resolve, reject) => { setTimeout(() => { if (id > 0) { resolve({ id, name: "Admin" }); // success } else { reject(new Error("Invalid user ID")); // failure } }, 1000); }); // Consuming with .then() / .catch() fetchUser(1) .then(user => { console.log(`Got user: ${user.name}`); return fetchOrders(user.id); // chained! }) .then(orders => { console.log(`Orders: ${orders.length}`); }) .catch(error => { console.error(`Error: ${error.message}`); }) .finally(() => { console.log("Done"); // always runs });

Promises are chainable — no more nesting. But .then().then().then() chains are still harder to read than synchronous code.

Promise States — Three Possible States

PENDING

Operation still in progress. Neither resolved nor rejected yet.

e.g. fetch() in flight

FULFILLED

Succeeded. Has a result value. .then() callback runs.

e.g. data received

REJECTED

Failed. Has an error reason. .catch() callback runs.

e.g. network error

Transitions: Pending → Fulfilled  |  Pending → Rejected — never backwards, never twice. Once settled, a Promise is immutable.

When you await a Promise, code pauses at Pending and resumes when Fulfilled (gets the value) or throws when Rejected.

Era 3: async / await

Promise Chain Version

function loginTest() { return page.goto('/login') .then(() => page.fill('#user', 'admin')) .then(() => page.fill('#pass', 'Admin1234')) .then(() => page.click('#login')) .then(() => page.waitForURL('/dashboard')) .then(() => expect(page.url()).toContain('/dashboard')) .catch(err => console.error(err)); }

async/await Version (Playwright Style)

async function loginTest(page) { await page.goto('/login'); await page.fill('#user', 'admin'); await page.fill('#pass', 'Admin1234'); await page.click('#login'); await page.waitForURL('/dashboard'); expect(page.url()).toContain('/dashboard'); }

async/await is NOT a different mechanism — it's syntax sugar over Promises that reads like synchronous code.

The Critical Rules of async/await

// RULE 1: async functions always return a Promise async function getUser() { return "Admin"; // actually returns Promise.resolve("Admin") } // RULE 2: await can ONLY be used inside an async function async function test() { const user = await getUser(); // OK — inside async function } // const user = await getUser(); // SyntaxError — top level (unless module) // RULE 3: await pauses THIS function only — not the whole program async function runTests() { console.log("start"); const result = await page.goto("/login"); // pauses here until done console.log("navigation complete"); // runs after goto resolves } // RULE 4: Forgetting await = getting a Promise object, not the value! const title = page.title(); // Promise object — NOT the title string const title2 = await page.title(); // "Login Page" — actual string

The most common Playwright bug: forgetting await before async calls. Always check if a method is async.

Error Handling in async Functions

// try/catch replaces .catch() in async/await world async function performLogin(page, creds) { try { await page.goto('/login'); await page.getByLabel('Username').fill(creds.username); await page.getByLabel('Password').fill(creds.password); await page.getByRole('button', { name: 'Login' }).click(); await page.waitForURL('**/dashboard', { timeout: 10000 }); return true; } catch (error) { // Playwright throws TimeoutError, Error, etc. console.error(`Login failed: ${error.message}`); return false; } } // Unhandled rejection — crashes the test // async function badTest() { // await page.goto('/nonexistent'); // throws, but nothing catches it // } // Playwright catches uncaught errors in test body automatically // But inside helper functions, YOU must handle errors

Playwright surfaces async errors with full stack traces in Trace Viewer. Understanding async errors helps you debug fast.

All 6 Promise Methods — Quick Reference

Promise.all()

All must succeed. Returns array of values. Fails immediately if any promise fails. Best for: parallel test setup.

Promise.allSettled()

Wait for all, see each result. Never rejects — each result has status: fulfilled | rejected. Best for: checking all results.

Promise.race()

First to settle wins — success or failure. Race an operation against a timer. Best for: custom timeouts.

Promise.any()

First success wins. Only rejects if ALL fail. Best for: trying multiple URLs or endpoints.

Promise.resolve(val)

Already-resolved promise. Wraps a value in a Promise instantly. Best for: mock/stub return values.

Promise.reject(err)

Already-rejected promise. Wraps an error instantly. Best for: mocking failure scenarios.

In tests: Promise.all() for parallel API setup, Promise.allSettled() to check all results, Promise.race() for timeouts.

The Event Loop — Mental Model

Call Stack

Currently executing code. Synchronous only. One thing at a time.

Web APIs / Node APIs

setTimeout, fetch, file reads run here in background threads.

Callback Queue

Completed async tasks wait here until the call stack is empty.

The Loop

The event loop continuously checks: "Is the call stack empty?" If yes, it picks the next item from the callback queue and runs it. This is how JS handles async without multiple threads.

Playwright's await lets the event loop process other work while waiting for browser operations.

Microtasks vs Macrotasks (Quick Overview)

console.log("1 — synchronous start"); setTimeout(() => console.log("5 — setTimeout (macrotask)"), 0); Promise.resolve() .then(() => console.log("3 — Promise .then (microtask)")) .then(() => console.log("4 — chained .then (microtask)")); console.log("2 — synchronous end"); // Output order: // 1 — synchronous start // 2 — synchronous end // 3 — Promise .then (microtask) ← microtasks run before macrotasks! // 4 — chained .then (microtask) // 5 — setTimeout (macrotask)

Microtasks (Higher Priority)

  • Promise .then() / .catch()
  • async/await continuations
  • Run before any macrotask

Macrotasks (Lower Priority)

  • setTimeout / setInterval
  • DOM events, I/O
  • Run after all microtasks clear

Common Async Mistakes in Playwright

Mistakes

// Missing await — gets Promise, not value const text = page.textContent('.title'); expect(text).toBe("Login"); // FAILS: text is Promise // await in forEach — BROKEN urls.forEach(async (url) => { await page.goto(url); // forEach doesn't await! }); // Test ends before navigations complete // Mixing then() with await const result = await fetch('/api') .then(r => r.json()); // valid but confusing

Fixes

// Always await async calls const text = await page.textContent('.title'); expect(text).toBe("Login"); // ✓ // Use for...of for async iteration for (const url of urls) { await page.goto(url); // correctly sequential } // Or Promise.all for parallel await Promise.all( urls.map(url => page.goto(url)) );

Async/Await in Playwright: The Full Picture

import { test, expect } from '@playwright/test'; // test() callback MUST be async — all Playwright actions are async test('complete login flow', async ({ page }) => { // Every browser interaction is awaited await page.goto('https://demo.app/login'); // Locator actions are async await page.getByLabel('Username').fill('admin'); await page.getByLabel('Password').fill('Admin1234!'); await page.getByRole('button', { name: 'Login' }).click(); // Assertions in Playwright have built-in auto-retry (they're async too) await expect(page).toHaveURL(/dashboard/); await expect(page.getByText('Welcome, Admin')).toBeVisible(); // page.evaluate runs code in the browser context const pageTitle = await page.evaluate(() => document.title); expect(pageTitle).toBe('Dashboard — Demo App'); });

Rule: If a Playwright method returns a Promise — which is most of them — you must await it. VS Code shows the return type when you hover.

Playwright Auto-Waiting — Built-in Intelligence

What Playwright Waits For Automatically

Before every action (click, fill, check…), Playwright checks:

  • Element is attached to the DOM
  • Element is visible (not hidden/display:none)
  • Element is stable (not animating)
  • Element is enabled (not disabled)
  • Element receives events (not covered by overlay)

Explicit waitFor Methods

// Wait for URL to change await page.waitForURL('**/dashboard'); // Wait for element state await page.waitForSelector('.toast'); // Wait for network idle await page.waitForLoadState('networkidle'); // Wait with custom timeout await expect(locator) .toBeVisible({ timeout: 10000 });

Never use page.waitForTimeout(3000) — it's a fixed delay and makes tests slow and flaky. Use event-based waiting instead.

Async in Hooks and Page Objects

Hooks Must Be async

test.beforeEach(async ({ page }) => { await page.goto('/login'); await page.fill('#user', 'admin'); await page.click('#submit'); await page.waitForURL('/dashboard'); }); test.afterEach(async ({ page }) => { await page.close(); }); test.beforeAll(async () => { await createTestUser(); // API setup });

Page Object Async Methods

class LoginPage { constructor(page) { this.page = page; } async login(user, pass) { await this.page.fill('#user', user); await this.page.fill('#pass', pass); await this.page.click('#submit'); await this.page.waitForURL('/dashboard'); } } // In test: await loginPage.login('admin', 'Admin1!');

All Page Object methods must be async — they call Playwright actions. Every call in tests must use await.
