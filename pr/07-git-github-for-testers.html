Why Every Tester Needs Git

Without Git

  • test-v1.spec.ts, test-v2.spec.ts, test-FINAL.spec.ts
  • Can't undo a bad change
  • Can't collaborate without overwriting
  • No history of why a test was changed

With Git

  • Full history of every change with author + reason
  • Branch off, experiment, merge when ready
  • Revert to any point in history
  • Collaborate with PRs + code review

Git is not optional for SDET roles. Every job description requires it. It is also how you showcase your portfolio on GitHub.

Core Git Concepts

Repository

A folder with full version history stored in .git/. Can be local or remote (GitHub).

Commit

A snapshot of changes with a message. The atomic unit of Git history.

Branch

A parallel line of development. Work on features without affecting main.

Staging Area

The "draft" area — choose exactly which changes go into the next commit.

Remote

A copy of the repo on GitHub. push sends changes; pull gets them.

The Daily Git Workflow

# Initial project setup git init # create a new repo git clone https://github.com/org/repo # clone existing repo # Daily workflow git status # see what changed git add tests/login.spec.ts # stage specific file git add . # stage ALL changes git commit -m "feat: add login smoke test" # Remote sync git push origin main # push to GitHub git pull origin main # get latest changes # Branching git checkout -b feature/login-tests # create + switch to branch git checkout main # switch back git merge feature/login-tests # merge branch # History git log --oneline --graph # visual history git diff HEAD~1 # diff vs last commit # Undo git restore tests/login.spec.ts # discard unstaged change git reset HEAD~1 --soft # undo last commit, keep changes

Learn these 15 commands. They cover 95% of your daily Git work.

Branching Strategy for Test Frameworks

BranchPurposeRule
mainStable, working testsNever commit directly
developIntegration branchMerge feature branches here first
feature/login-testsNew test suiteOne feature = one branch
fix/flaky-checkout-testBug fix in existing testFix + PR + merge
chore/update-playwrightDependency updateAlways in separate branch

Convention: type/description-in-kebab-case. Types: feat, fix, chore, refactor, docs

Commit Messages — Conventional Commits

# Format: type(scope): description # Body (optional) # Footer (optional) # Good commit messages git commit -m "feat(auth): add login tests for admin and viewer roles" git commit -m "fix(checkout): handle timeout on payment page" git commit -m "chore(deps): update @playwright/test to v1.52" git commit -m "refactor(pom): extract header component into BasePage" git commit -m "docs: add README with setup instructions" # Bad commit messages (avoid) # git commit -m "fix" # git commit -m "updates" # git commit -m "WIP" # git commit -m "checkpoint" # Types: feat, fix, docs, style, refactor, test, chore, perf, ci

Conventional Commits are machine-readable: tools like semantic-release auto-generate changelogs from them.

The Pull Request (PR) Workflow

①

Create feature branch

②

Commit changes with good messages

③

Push branch to GitHub

④

Open PR for code review

⑤

Merge to main

Good PR Description Contains

  • What the change does (summary)
  • Why it was needed (context)
  • How to test it (reviewer steps)
  • Screenshots/traces if applicable

PR Review Checklist

  • No hardcoded credentials
  • Tests follow POM pattern
  • Assertions after every action
  • CI pipeline passes

GitHub Actions — CI for Playwright

# .github/workflows/playwright.yml name: Playwright Tests on: push: branches: [main, develop] pull_request: branches: [main] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: '22' cache: 'npm' - name: Install dependencies run: npm ci - name: Install Playwright browsers run: npx playwright install --with-deps - name: Run Playwright tests run: npx playwright test - uses: actions/upload-artifact@v4 if: always() with: name: playwright-report path: playwright-report/

Every push runs tests automatically. Broken tests block the merge. This is Continuous Integration in action.
