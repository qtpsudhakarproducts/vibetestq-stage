Environment-Specific Configurations

// .env.dev BASE_URL=http://localhost:3000 API_URL=http://localhost:4000/api // .env.staging BASE_URL=https://staging.myapp.com API_URL=https://api-staging.myapp.com // .env.prod BASE_URL=https://myapp.com API_URL=https://api.myapp.com // package.json scripts { "scripts": { "test:dev": "ENV=dev npx playwright test", "test:staging": "ENV=staging npx playwright test", "test:prod": "ENV=prod npx playwright test --grep @smoke", "test:ui": "npx playwright test --ui", "test:debug": "npx playwright test --debug" } }

Never hardcode environment URLs in tests. Always use baseURL from config, which reads from environment variables.

Reporters and Trace Files

Built-in Reporters

  • html — rich visual report in browser
  • list — one line per test in terminal
  • dot — minimal: . ✗ in terminal
  • junit — XML for Jenkins/CI systems
  • json — structured data for custom tools
  • github — GitHub Actions annotations

Trace File Usage

  • Set trace: 'on-first-retry' in config
  • Generates .zip on test failure
  • npx playwright show-trace
  • Shows timeline + DOM snapshots
  • Network requests per step visible
  • Console logs and source code

Always combine html + junit reporters in CI. Use trace: 'on-first-retry' — always on is too slow, never means blind debugging.

Parallelism and Sharding

// playwright.config.ts — workers setting export default defineConfig({ workers: process.env.CI ? 4 : undefined, // undefined = CPU count fullyParallel: true, // tests within a file also run in parallel }); // Sharding — split suite across multiple CI machines // Machine 1 of 3: npx playwright test --shard=1/3 // Machine 2 of 3: npx playwright test --shard=2/3 // Machine 3 of 3: npx playwright test --shard=3/3 // GitHub Actions matrix example: // matrix: // shardIndex: [1, 2, 3, 4] // shardTotal: [4] // run: npx playwright test --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }} // Merge sharded reports npx playwright merge-reports ./blob-reports --reporter html

Sharding = horizontal scaling. 4 shards on 4 CI machines = 4x faster test suite. Essential for suites with 500+ tests.
