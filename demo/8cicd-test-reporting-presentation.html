What is CI/CD?

Think of it as the "Automatic Quality Checkpower."

CI: Continuous Integration

Frequent code merges. Catching bugs as they land in the repository.

CD: Continuous Delivery

Keeping the app ready for customers at all times through automation.

CI/CD turns human manual effort into repeatable machine logic.

CI/CD in Real Life

Cookie Baking Analogy

Without CI/CD: Bake ALL 100 cookies → THEN taste → If salty, wasted 2 hours!
With CI/CD: Taste batter after EACH ingredient → Fix instantly → Perfect cookies!

Car Wash Analogy

Without CI/CD: Wash 10 cars → Check at end → Soap missing → 10 dirty cars!
With CI/CD: Check EACH car immediately → Fix before next → All clean!

GitHub Actions: The Command Center

What is GitHub Actions?

GitHub Actions is an automation service built into GitHub that runs commands when events happen (like pushing code).

Why GitHub Actions?

  • Free Virtual Machines: GitHub gives you servers (Ubuntu, Windows, macOS) for free (2000 mins/month).
  • Auto-Trigger: Tests run automatically when you push code — no manual steps.
  • Integrated: Results appear directly in your GitHub repository.

Inside the GitHub Actions Runner

Runner = A virtual machine (VM) — essentially a temporary computer in GitHub's data center.

What Happens Inside the Runner?

1 GitHub creates a fresh Ubuntu VM (like a new computer).

2 Downloads your code from the repository.

3 Installs Node.js (v20), npm, and dependencies (npm ci).

4 Installs Playwright browsers (npx playwright install).

5 Runs your tests (npx playwright test).

6 Destroys the VM (no trace left behind).

Important: Each run gets a brand-new VM. Nothing is saved between runs.

Where Do Browsers Actually Run?

Local Execution

Location: Your laptop

Browsers: Installed on your machine

Visible: You see browser windows

Speed: Limited by your CPU

GitHub Actions

Location: GitHub's data center (AWS/Azure)

Browsers: Installed on the runner VM

Visible: NO — headless mode (no screen)

Speed: Powerful cloud servers

Key Insight: Browsers run inside the virtual machine in GitHub's cloud — not on your laptop!

Headless Execution: No Screen Required

Headless Mode = Browser runs without a visible window — no screen, no mouse cursor.

Headed (Normal)

Browser window opens. You see pages loading.

Use: Debugging locally

Headless

Runs in memory only. No UI rendered. Invisible.

Use: CI/CD servers

Why Headless? GitHub VMs have no monitor. 30-50% faster — skips rendering pixels.

// playwright.config.ts use: { headless: true, // ← Always true on CI }

The Complete Execution Flow

1 You Push Code → Git pushes changes to GitHub repository

2 GitHub Detects Push → Reads .github/workflows/tests.yml

3 Workflow Starts → GitHub spins up a fresh Ubuntu VM

4 Setup Phase → Installs Node.js, npm packages, Playwright browsers

5 Test Execution → npx playwright test runs in headless mode

6 Browsers Launch → Chromium/Firefox/WebKit start inside the VM

7 Tests Run → All page interactions happen in memory on cloud server

8 Results Collected → Screenshots, traces, logs saved

9 Sent to ReportPortal → Results uploaded to dashboard

10 VM Destroyed → GitHub deletes the runner (clean slate)

Remember: Everything happens on GitHub's server, not your machine!

Playwright Execution Flow

1. Discover: Scan for all test files.

2. Setup: Initialize browsers (Chromium, WebKit, Firefox).

3. Headless Run: Invisible execution for maximum speed.

4. Teardown: Kill processes and collect artifacts.

# The magic command npx playwright test

Where Files Live: Project Structure

Understanding WHERE to create files is critical!

my-playwright-project/ +-- .github/ ← CREATE THIS! +-- workflows/ ← CREATE THIS! +-- tests.yml ← WORKFLOW HERE +-- tests/ +-- login.spec.ts +-- checkout.spec.ts +-- playwright.config.ts ← REPORTPORTAL CONFIG +-- package.json

Critical: The .github/workflows/ folder MUST be at the root!

The Power of Parallelism

Workers are independent processes that run tests in parallel.

Local (Sequential)

100 tests @ 1 min each = 100 mins.

CI/CD (Parallel)

100 tests @ 10 workers = 10 mins.

Workers make automation feasible for large enterprise suites.

Configuring: playwright.config.ts

Optimize for CI environment:

export default defineConfig({ // Use 1 worker on CI to avoid memory crashes workers: process.env.CI ? 1 : undefined, // High stability: Retry failed tests on CI retries: process.env.CI ? 2 : 0, use: { headless: true, screenshot: 'only-on-failure', trace: 'retain-on-failure', } });

Configuring: GitHub Actions Workflow

Create .github/workflows/tests.yml:

name: Playwright Tests on: [push, pull_request] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: '20' - run: npm ci - run: npx playwright install --with-deps - run: npx playwright test env: RP_TOKEN: ${{ secrets.RP_TOKEN }}

YAML Explained: Line-by-Line

name: → What you'll see in GitHub Actions tab

on: [push, pull_request] → WHEN tests run (on every push/PR)

runs-on: ubuntu-latest → WHICH operating system (Ubuntu Linux)

actions/checkout@v4 → Downloads your code to the VM

actions/setup-node@v4 → Installs Node.js version 20

npm ci → Installs dependencies (faster than npm install)

npx playwright install → Downloads browser binaries

npx playwright test → EXECUTES YOUR TESTS!

secrets.RP_TOKEN → Secure environment variable for ReportPortal

Each step runs sequentially. If one fails, the workflow stops.

Navigating GitHub: The Actions Tab

After pushing code, here's how to see your test results:

1 Go to: https://github.com/YourUsername/YourRepo

2 Click: Actions tab (top navigation)

3 You'll see workflow runs with status:

The "Local Report" Trap

  • No historical trend or comparison.

What's Required?

To connect your automation to the dashboard:

1. API Key: Your secret token.

2. Project Name: Your workspace ID.

3. Endpoint: The server URL.

Store these in GitHub Secrets for security.

How to Add GitHub Secrets (Step-by-Step)

Secrets are encrypted environment variables stored securely in GitHub.

1 Go to your repository on GitHub

2 Click: Settings (top-right)

3 Left sidebar: Click Secrets and variables → Actions

4 Click: New repository secret

5 Name: RP_TOKEN

6 Value: Paste your ReportPortal token

7 Click: Add secret

Security: Secrets are encrypted and never visible in logs (shown as ***).

ReportPortal Integration

Add to playwright.config.ts:

// In playwright.config.ts reporter: [ ['list'], // Keep console output ['html'], // Keep local HTML report ['@reportportal/agent-js-playwright', { apiKey: process.env.RP_TOKEN, endpoint: 'https://demo.reportportal.io/api/v1', project: 'vibetestq_personal', launch: 'Playwright CI Tests', description: 'Automated tests from GitHub Actions', attributes: [ { key: 'env', value: 'staging' }, { key: 'browser', value: 'chromium' }, ], }] ]

Common Issues & Quick Fixes

❌ Issue: "Cannot find module '@playwright/test'"

✅ Fix: Ensure npm ci step exists in workflow before running tests.

❌ Issue: "Executable doesn't exist at chromium path"

✅ Fix: Add npx playwright install --with-deps step in workflow.

❌ Issue: Tests pass locally, fail on CI

✅ Fix: Increase timeouts, add retries, check viewport size (1280x720).

❌ Issue: ReportPortal 401 Unauthorized

✅ Fix: Verify RP_TOKEN secret is set correctly in GitHub Settings.
