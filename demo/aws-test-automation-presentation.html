What is AWS?

Amazon Web Services (AWS)

A massive technology supermarket where you rent computers, storage, and services by the hour instead of buying them.

The Uber Analogy

Owning a Car (Traditional)

  • Buy for $30,000
  • Sits in garage 23 hours/day
  • You maintain it

Using Uber (AWS)

  • Pay $10 per ride
  • Use only when needed
  • Driver maintains it
  • Variable low cost

Cloud = Renting computing power instead of owning it

Instead of running tests on your laptop, you run them on a cloud computer.

  • Node.js / Python / Java

  • Browsers (Chrome, Firefox)
  • Your test code

Why Automation Engineers Like It

  • ✅ Full control over environment
  • ✅ Easy debugging via SSH
  • ✅ Same as local setup
  • ✅ Good for learning cloud
  • ⚠️ You manage it yourself

Option 2: Managed CI (CodeBuild / GitHub Actions)

"Hotel Room for Tests"

Simple Meaning: A machine is created only when tests run, and destroyed afterward.

Check in → Run tests → Leave → Room cleaned

Every test run gets a fresh machine. You don't manage servers.

Examples

  • AWS CodeBuild - AWS native CI
  • GitHub Actions - GitHub runners
  • GitLab CI - GitLab runners
  • Azure Pipelines - Microsoft agents

Why Teams Use It

  • ✅ No server maintenance
  • ✅ Easy CI/CD integration
  • ✅ Auto clean environment
  • ✅ Good for PR validation
  • ⚠️ Harder debugging
Code Pushed
Runner Created
Tests Run
Runner Destroyed

Option 3: Serverless Execution (AWS Lambda)

"Tests Run Without Servers"

Simple Meaning: Tests run inside functions, not machines.

Press switch → Test runs → Disappears

No machine exists before or after execution.

✅ Why It's Interesting

  • Extremely cheap for small workloads
  • Auto-scaling (0 to 1000s)
  • No server management
  • Pay only per execution

❌ Limitations

  • Complex setup (packaging)
  • 15-minute execution limit
  • Hard debugging
  • Headless browsers only
  • Cold start delays

Best Use Cases

✓ Smoke tests (5-10 tests) | ✓ Health checks | ✓ Event-triggered validation | ✓ API testing

Not recommended for: Full UI test suites (use EC2 instead)

GitHub Actions vs AWS EC2: Complete Comparison

GitHub Actions

Location: GitHub's data center

Setup: Minimal (YAML file)

Cost: 2000 mins/month FREE

Control: Basic (preset VMs)

Specs: 2-core CPU, 7GB RAM (fixed)

OS: Ubuntu/Windows/macOS

Browsers: Headless only

Parallel: Max 20 workers (Enterprise)

Lifecycle: Auto-destroyed after run

Maintenance: Zero (fully managed)

AWS EC2

Location: Your AWS account

Setup: Complete (instances, security)

Cost: Pay per second used

Control: Full (any VM size)

Specs: 1-96+ cores, 0.5-768GB RAM

OS: Ubuntu/Windows (your choice)

Browsers: Headless or GUI (VNC)

Parallel: Unlimited instances

Lifecycle: Manual termination

Maintenance: You manage updates

Analogy: GitHub Actions = Hotel room (ready to use) | AWS EC2 = Apartment (customize everything)

When to Use What?

✅ Use GitHub Actions When:

  • Test suite runs < 30 minutes
  • Standard VM specs are enough (2 CPU, 7GB RAM)
  • Want zero infrastructure management
  • Budget is tight (free tier sufficient)
  • Simple CI/CD pipeline needed

✅ Use AWS EC2 When:

  • Test suite runs > 1 hour (or 1000+ tests)
  • Need powerful VMs (8+ CPU cores)
  • Want complete control over environment
  • Need to keep instances running
  • Testing across multiple regions

Creating AWS Resources Using the Console

Why Use the AWS Console?

  • Beginner-friendly, no code required
  • Visual step-by-step process
  • Great for learning and one-time setup

Tip: The Console is like AWS's "Control Panel"—point, click, and create resources!

Key Terms When Creating AWS Resources

EC2 Terms

  • AMI (Amazon Machine Image) = Pre-installed OS template (like Windows installer)
  • Instance Type = Computer size (CPU/RAM) like t3.medium
  • Key Pair = Digital key to unlock/access your instance (like house key)
  • Security Group = Firewall rules (who can enter)
  • Public IP = Internet address to reach your instance

General Terms

  • Region = Data center location (Mumbai, Virginia, etc.)
  • SSH = Secure way to connect to remote computers
  • VNC = Remote desktop for GUI access
  • User Data = Script that runs on instance startup
  • Tags = Labels for organizing resources (Name=TestServer)

Remember: These terms appear in the Console—we'll explain S3 & IAM in detail later!

Step-by-Step: Launching EC2 Instance (Part 1)

Getting Started

  1. Log in to AWS Console
  2. Search for EC2 in the top search bar and select it
  3. Click orange Launch Instance button
  4. Name: Enter friendly name (e.g., playwright-test-machine)
  5. AMI (OS): Select Ubuntu 22.04 LTS (free tier eligible)
    → This is your operating system
  6. Instance Type: Choose t3.medium (2 vCPU, 4GB RAM)
    → Computer power

Next: Configure security settings and launch!

Step-by-Step: Launching EC2 Instance (Part 2)

Security & Launch

  1. Key Pair: Click "Create new key pair" → Name it test-key → Download .pem file
    → Your SSH password (save it safely!)
  2. Security Group: Check "Allow SSH from My IP"
    → Firewall rule (restricts access to your IP only)
  3. Storage: Leave default (30 GB)
  4. Click Launch Instance → Wait 60 seconds
  5. Go to "Instances" → Copy Public IPv4 address
    → Your cloud computer's address

Done! Your cloud computer is ready. Connect using: ssh -i test-key.pem ubuntu@YOUR-IP

Understanding Key Pair & Security Group

Key Pair (SSH Key)

What is it? A digital key to access your EC2 instance securely.

Analogy: Like your house key—without it, you can't enter!

Important:

  • Download happens only once
  • Store safely (you can't re-download)
  • Use .pem for Mac/Linux, .ppk for Windows
  • Set permissions: chmod 400 test-key.pem

Security Group (Firewall)

What is it? Rules that control who can connect to your instance.

Analogy: Like a bouncer—only approved IPs can enter!

Common Rules:

  • SSH (Port 22): Allow from "My IP" only
  • HTTP (Port 80): Allow from anywhere (for web servers)
  • HTTPS (Port 443): Allow from anywhere (for secure web)

Security Warning: Never allow SSH from 0.0.0.0/0 (everywhere)—hackers will break in!

Creating S3 Bucket (Console)

S3 Bucket Setup

S3 buckets store test reports, screenshots, and videos in the cloud.

Steps

  1. Search for S3 in Console
  2. Click Create bucket
  3. Bucket name: Enter globally unique name
    → e.g., vibetestq-reports-2026
    (must be unique across all AWS)
  4. Region: Choose closest to you
    → e.g., us-east-1 (Virginia) or ap-south-1 (Mumbai)
  5. Uncheck "Block all public access" if sharing reports
    → Leave checked for private data
  6. Click Create bucket

Done! Your S3 bucket is ready to store test artifacts.

Creating IAM User (Console)

IAM User Setup

IAM users allow programs and scripts to access AWS resources securely.

Steps

  1. Search for IAM in Console
  2. Click Users → Create user
  3. Username: automation-user
  4. Click Next → Attach policies directly
  5. Search and select:
    → AmazonEC2FullAccess (launch instances)
    → AmazonS3FullAccess (upload reports)
  6. Click Create user
  7. Go to user → Security credentials → Create access key
  8. Select "CLI" → Download CSV (SAVE IT!)

Critical: Save the CSV file immediately. You cannot retrieve the secret key again!

Understanding S3 & IAM Concepts

S3 Bucket Explained

What is it? A cloud storage container for files (reports, screenshots, videos).

Analogy: Like Google Drive or Dropbox folder, but for AWS.

Key Points:

  • Globally unique name: No two buckets in the world can have the same name
  • Region matters: Choose nearest for speed, or same as EC2
  • Cost: $0.023/GB/month (10GB = $0.23/month)
  • Access: Can be private or public (based on settings)

IAM User & Access Keys

What is it? A user account for programs/scripts to access AWS (not for humans logging in).

Analogy: Like creating a "robot employee" with specific permissions.

Access Keys:

  • Access Key ID: Username (e.g., AKIAIOSFODNN7EXAMPLE)
  • Secret Access Key: Password (shown only once!)
  • Use case: GitHub Actions, Jenkins, or local scripts
  • Security: Never commit to Git, use environment variables

Critical: Access keys = Full AWS account access. Never share or expose them publicly!

Troubleshooting: Can't SSH

Problem

ssh -i key.pem ubuntu@ec2-ip → Connection timeout

Solutions

  • Check security group allows SSH from your IP
  • Verify your current IP: curl ifconfig.me
  • Check instance is running: aws ec2 describe-instances
  • Try EC2 Instance Connect (browser-based)
  • Verify key permissions: chmod 400 key.pem

Troubleshooting: Tests Fail on EC2

Problem

Tests pass locally but fail on AWS EC2

Solutions

  • Check browser versions match local
  • Ensure headless mode: headless: true
  • Run Playwright deps: playwright install-deps
  • Check memory: free -h (add swap if low)
  • Review CloudWatch logs for errors
  • Run with debug: DEBUG=pw:api npx playwright test

Troubleshooting: High AWS Bill (Part 1)

Problem

Expected $10/month, got $300 bill!

Investigation Commands

  • Check running instances:
    aws ec2 describe-instances --filters "Name=instance-state-name,Values=running"
  • Check stopped instances (still cost $):
    aws ec2 describe-instances --filters "Name=instance-state-name,Values=stopped"
  • Review EBS volumes: aws ec2 describe-volumes
  • Check snapshots: aws ec2 describe-snapshots --owner-ids self

Troubleshooting: High AWS Bill (Part 2)

Solutions

  • Terminate all unused instances (not just stop them)
  • Delete unattached EBS volumes
  • Remove old snapshots
  • Review S3 storage usage and clean up

Prevention

  • Set up auto-termination Lambda function
  • Enable Cost Anomaly Detection
  • Tag all resources for tracking
  • Use AWS Budgets with $20 alert threshold

Pro Tip: Check AWS Cost Explorer daily during first month to understand spending patterns
