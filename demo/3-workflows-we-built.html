WF1 · The Real Prompt We Run

# Task: Generate test scenarios from a requirement ## Context files (read in order) 1. .ai/project-context.md 2. .ai/conventions.md 3. requirements/REQ-{id}.md 4. .ai/graph.json ## Your job 1. Read the requirement fully 2. Detect ambiguity - list anything vague 3. Generate scenarios: happy path, edge cases, error states 4. Link every scenario to REQ-ID ## Rules - NEVER invent acceptance criteria not in the requirement - If ambiguity exists, LIST IT. Don't guess. - Scenarios must be executable by a tester ## Output Write to: scenarios/REQ-{id}-scenarios.md Append to graph.json

This prompt is in our repo at .ai/prompts/wf1-generate-scenarios.md — versioned like code.

[60 sec] "This is the actual prompt file. Versioned. PR-reviewed. 40 lines. That's it. No secret sauce."

WF1 · What Broke First Time

The prompt was too polite.

Our first version said: "If you notice ambiguity, please list it."

Claude interpreted "please" as optional. It generated scenarios with confident-looking guesses for every gap.

BA never got asked clarifying questions. Dev built on guesses. Staging surfaced 3 bugs that were really spec ambiguities.

What we changed

Replaced polite language with strict rules: "NEVER invent acceptance criteria. If ambiguity exists, LIST IT. Don't guess."

Capital letters. No politeness. AI models respect strictness.

Lesson: prompts are code. Draft, test, harden.

[75 sec — honest moment] Slow down. This is the trust builder. "We made this mistake. Here's exactly how. Here's what we changed." Quote both versions of the prompt — the old polite one and the new strict one. Don't minimize it.

WF7 · The 30 Lines (abridged)

export async function healingLocator(page, selector, intent) { try { const loc = page.locator(selector); await loc.waitFor({ timeout: 5000 }); return loc; } catch (err) { // Original failed — ask Claude for a working selector const dom = await page.content(); const screenshot = await page.screenshot(); const newSelector = await askClaudeForSelector(dom, screenshot, selector, intent); if (newSelector === "NO_HEAL") throw err; // NON-NEGOTIABLE: log every heal await logHeal({ timestamp: new Date().toISOString(), original: selector, proposed: newSelector, intent, test: testName }); return page.locator(newSelector); } }

Full file including logHeal and askClaudeForSelector ≈ 60 lines. That's the entire implementation.

[60 sec] "Look at line 13-14. The comment says NON-NEGOTIABLE. Every single heal gets logged. No silent fixes. That's the rule that saved this workflow from becoming an anti-pattern."

WF7 · What Broke First Time

The near-miss: a silent heal almost shipped a real bug.

Week 2 of WF7. A selector for [data-testid="confirm-order"] started healing. Once. Twice. Four times in a day.

Each heal passed. Dashboard stayed green. Nobody had a reason to look.

On Friday morning, a user reported a stuck checkout. The button had been moved to a confirmation modal by a dev PR. Tests were clicking a similar button elsewhere on the page — a button that had nothing to do with confirming the order.

AI didn't lie. It found a button that looked plausible. But plausible ≠ correct.

What we changed

Added the 5-heals-per-week escalation rule. Same selector healing more than 5 times → WF7 refuses to heal and fails loudly. Plus: weekly heal log review, no exceptions.

[90 sec — the key moment of this workflow] This is the story that makes the whole talk credible. Tell it slowly. Admit you almost shipped a bug. THEN explain the fix. Audiences respect honesty — they get suspicious of "it just worked."

BEFORE

Jira ticket closed as "Fixed — deployed to prod."

6 weeks later — same bug. Same alert. Same fix.

Nobody asked: "Why didn't we have a regression test?"

AFTER

Datadog webhook → MCP agent correlates to graph.json.

Agent proposes a regression scenario + identifies why existing tests missed it.

QA reviews, approves. WF5 generates the automated test for next sprint.

Same bug never recurs.

Repeat bugs last 6 months: {1 (and we learned from it)}

A human approves. A human does not write. The loop is the product.

WF11 · What Broke First Time

We overtriggered. The backlog exploded.

First version of WF11 triggered on every Datadog alert — including third-party outages, flaky network retries, and cron job warnings.

By end of Week 1: 47 WF11-generated Jira tickets. Most were noise. QA spent a whole day cleaning up.

Team's trust in the workflow cratered. "This thing is spam."

What we changed

Wrote strict triggers in .ai/conventions/production-feedback-rules.md — only trigger on P0/P1 OR recurrence 3+ times OR >1% users affected. Everything else: skip.

Trigger rate dropped from 47/week to ~3/week. Signal, not noise.

Lesson: AI workflows must have strict "when not to trigger" rules before "when to trigger" rules.

[75 sec] "47 tickets in a week. The team wanted to kill the workflow. We didn't — we fixed the triggers. That's the general lesson: tune the noise filter BEFORE scaling. Every AI workflow needs a 'when NOT to act' rule."

Recommendation for learners:
