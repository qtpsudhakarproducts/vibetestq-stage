Mistake #1 — We Chose Disconnection

💬 Quick question: What tools does your team use for project management, code, and test cases? Are they from the same vendor?

What was offered

  • Atlassian: Jira + Bitbucket (ready, integrated)
  • Azure DevOps: PM + Repos + Test Plans
  • GitLab: PM + Code + CI/CD

What we chose

  • Jira for PM — but GitHub for code
  • Azure DevOps for code — but Jira for PM
  • TestRail separately. Confluence separately. Slack separately.

We didn't inherit fragmentation. We chose it. Tool by tool. Decision by decision.

Mistake #2 — We Never Cared About Traceability

💬 Be honest — when code changed last sprint, did anyone know which tests to re-run, or did you just re-run everything?

What we loved

  • Manual regression planning every release
  • Root-cause-by-memory (ask the senior tester)
  • "Let's just re-run the full suite"
  • Tribal knowledge in people's heads

What we never built

  • Which tests are impacted by this code change?
  • Which requirement does this code implement?
  • What regression risk did my commit just introduce?

AI didn't break our SDLC. It exposed a debt we refused to pay.

From Code Repository → Project Repository

Code Repository (yesterday)

  • Source code only
  • Requirements in Jira
  • Tests in TestRail
  • Decisions in Slack
  • Docs in Confluence
  • AI sees one slice of your project.

Project Repository (today)

  • Requirements — machine-readable
  • Code — linked to requirements

  • Decisions — captured as context
  • Bugs — linked to code and tests

Wait — Am I Saying "Replace Jira"?

💬 I just said "Project Repository." But your team uses Jira and TestRail today. Both things cannot be true. So which is it?

The Project Repository doesn't replace Jira. It adds a new layer on top.

Jira + TestRail (keep)

Own the human process layer. Sprint ceremonies, tickets, approvals, dashboards.

Project Repository (add)

Owns the machine context layer. Linked graph of requirements, code, tests, decisions. What AI reads.

Nothing is thrown away. A new layer is built above.

The Artifact: graph.json

💬 How does this file get created? Nobody writes it by hand — AI generates and maintains it.

How it's created

# Every AI commit triggers: AI-agent scans the diff → linked REQ-ID → updated code_files → linked test_files → fresh coverage numbers graph.json updated → committed with code → reviewed in the PR # No manual linking, ever.

Sample entry

{ "requirement_id": "REQ-142", "title": "Password reset", "code_files": [ "src/auth/reset.ts" ], "test_files": [ "tests/auth/reset.spec.ts" ], "coverage": 94 }

Living file. AI creates it. AI updates it. AI queries it.

Act 6 — The QA Workflows

Design · Execution · Intelligence

A QA Workflow Is Not a Test Case

💬 If I ask for "your workflows" — most teams send me a test case template. That's not a workflow. Here's the difference.

A test case

  • Preconditions, steps, expected result
  • One-time artifact
  • Stops when the test ends

A workflow

  • End-to-end loop across the SDLC
  • Continuous — repeats every sprint
  • Learns from production and feeds back

A test case fires once. A workflow runs forever.
