The idea

Two stages of quality.
Never mixed.

A project keeps two live pictures of quality. What is built while the feature is being made, and what is proven when the release is tested. Forge shows them side by side and lets a person promote from one to the other.

Development stage

Built while the feature is made

Scenarios, automated specs, pages and locators, findings and proposals from the GenEx Agent, developers and QA. Informal, continuous, never counted as release results.

  • Explore: what the agent found in the application
  • Proposals waiting for a person's decision
  • Development quality dashboard
promote→
Release stage

Proven when the release is tested

Cycles run against accepted test versions, with evidence on every attempt and sign-off at the end. The formal record a release is judged on.

  • Published test cases, versioned
  • Cycles, executions, defects and evidence
  • Release health, readiness and sign-off

A development-stage scenario becomes a release test only when someone promotes it: promotion makes a draft test case, which is published under the project's policy.

Five modules

Everything a release needs,
in the order a team meets it.

01

Test cases

A versioned library in folders. Steps tables or Gherkin with examples, custom fields, import and export, and a publication policy: authors publish directly, or another author approves. An accepted version is what cycles run.

02

Test cycles

A planned run of chosen tests, in an environment, over a period. Plan, assign, start, pause, amend, complete. Release readiness and sign-off at the end, with the reasons beside every test.

03

Executions

The runner walks a person through a test step by step, on a desktop or a phone. Every attempt is kept with its evidence and the defects it linked. Automated results arrive from CI into the same history.

04

Reports

Predefined reports that work on day one, a builder for the ones your organization needs, traceability to requirements, exports, and published snapshots that stay as they were.

05

Dashboard

Where the project stands and what needs attention, release stage and development stage, arranged by each person for their own work.

The GenEx Agent inside Forge

It explores, drafts and validates.
People decide.

The agent works in the application and in the repository, and everything it learns is visible to the whole team in Forge.

  • Explore. Start an exploration of an application and environment. The agent maps screens, fields, controls and server calls, and reports findings with a severity: broken, should fix, or a note.
  • Propose. From a finding or a scenario the agent drafts a test case with the steps that reproduce it. Drafts wait in Proposals for an author to accept, edit or decline.
  • Generate. Reusable Playwright or Cucumber automation, with pages and locators kept as assets the team can see and rate as stable or fragile.
  • Validate. The agent runs scenarios against the developed feature and reports what it saw. Its runs sit in the development stage until a person promotes them.

The agent never presses Save, Delete or Submit, so what sits behind those is not mapped, and the screens it found but did not explore are counted as such. Its limits are stated on the Explore overview.

Generate tests from requirements

From selected Jira stories or pasted text, a draft test case per acceptance criterion, each linked to its source.

Convert scenarios

A pasted scenario, a .feature file or an agent scenario becomes a structured proposal: steps split, expected results added, missing test data flagged.

Suggest steps from a title

Inside a new test case, the steps filled in for the author to edit.

Review and improve

Clearer steps, missing expected results and tags for an existing case, shown as a difference to accept in parts.

Explain failures

A short likely cause for a failed attempt: the application, the test or the environment, with similar failures grouped. Advice, never a changed result.
